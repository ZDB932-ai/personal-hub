# Personal Hub 开源项目调研与优化建议

调研日期：2026-09-20。对象为当前工作区（包含未提交改动），不是仅依据 AGENTS.md 或某个历史提交。本文是研究建议，不代表已采纳的架构决策。

方法：核对 8 个项目的官方仓库或官方文档，抽查本项目数据模型、保存、同步、附件、规划和 AI 派发代码。没有部署这些对标项目，也没有对其做安全审计。外部默认分支和在线文档会变化；本文不以星数或版本号评价优劣。

本次执行 `npm run test -- --maxWorkers=2`：20 个测试文件、143 项通过。历史真机验收结论来自项目已有记录，本次没有重新运行真机验收，也没有修改产品代码。

## 1. 核心判断

Personal Hub 最值得发展的定位是：**本地优先、加密保存、跨设备使用的个人行动与资料工作台，并能把具体任务交给 AI 执行。**

你的优势在于长期计划、周计划、每日精力、资料、账号和 AI 控制已经处于同一个应用内。下一步最大收益来自让这些模块形成可追溯的工作流程，并让同步与恢复更容易理解。

建议围绕这条流程迭代：

> 随手收集 → 整理成任务或项目 → 关联资料 → 自己执行或派发 AI → 查看结果并验收 → 归档与复盘。

现有成熟实现应保留：随机数据密钥与密码封装、IndexedDB 原子提交、持久化在途同步操作、服务端幂等回执、冲突双方保留、附件密文传输和原生保存。没有充分理由为追求“更先进”整体替换这些底座。

## 3. 当前项目已完成什么

不要再将以下能力列为“从零建设”：

- v3 随机数据密钥、设备密码封装、旧库升级、离线加入和改密不重加密全部业务。
- IndexedDB Repository、串行保存、修订检查、离线操作日志。
- 逐条密文同步、删除墓碑、冲突保留、游标事务提交和重试幂等。
- 附件 1 MiB 密文分块与摘要校验，上传缺块补传。
- Web、Windows、Android 50 MiB 传输与恢复验证记录，原生文件保存专项。
- 完整备份跨主密码恢复、停机复制服务数据目录后的恢复演练。
- 任务快捷输入、标签、子任务、周计划、长期计划、每日精力、局部撤销。
- AI 连接凭据已经加密保存，不能因为看见普通配置使用 localStorage 就判定 Token 明文落盘。

依据：`src/lib/vaultKeys.ts`、`src/lib/recordSyncEngine.ts`、`src/lib/attachmentSync.ts`、`src/lib/aiopencode.ts:124`，以及 `docs/VERIFICATION-2026-09-20.md`、`docs/LARGE-FILE-VERIFICATION.md`、`docs/BACKUP-VERIFICATION.md` 的后续补充。

仍需准确区分：USB 转发联调不等于真实局域网/公网 HTTPS 验收；传输 50 MiB 成功不等于测过峰值内存；保存接口截取内容也不等于该类型文件的系统选择器完整验收。

## 4. 优先级最高的改进

### P0-A：让持续打开的设备能自动收到远端更新

**代码事实：** `src/lib/recordSync.ts:29` 监听本地保存、解锁/维护状态、online 和 focus；`recordSyncScheduler.ts` 处理防抖、后续工作和退避，没有常驻的周期拉取。设备一直处于前台且不发生本机修改时，远端更新缺少稳定触发入口。

**参考：** Joplin 在变更后上传，同时周期性拉取远端变更。其引擎和传输分层也支持你继续保留已有 `RecordSyncTransport`。[同步设计](https://joplinapp.org/help/dev/spec/sync/)

**建议：** 先实现仅在已解锁、在线、前台、未手动暂停时运行的周期拉取，例如 30–60 秒并加随机抖动；需要更低延迟时再增加只提示“有变化”的 SSE 通知。远端提示仍通过现有认证、游标和解密校验路径获取数据。

必须先拆开“拉取记录”与“检查所有附件”，避免每次定时拉取都解密和散列整个资料库。

**验收：** 两台设备同时保持打开，A 修改，B 无操作仍在目标时间内更新；锁定/暂停无请求；恢复后不重复上传。

### P0-B：AI 派发绑定目标、运行记录和结果

**代码事实：** `src/lib/aiopencode.ts:764` 的 `dispatchToAgent()` 直接取 `sessions[0]`，不存在才创建会话；入参只有标题和备注，返回 `Promise<void>`。`Task` 没有 AI 会话或运行关联。现状可能把新任务追加到不相关的既有会话，派发后也难以从任务追踪结果。

**建议：** 派发时明确 Agent、项目和目标会话。支持协议的 Agent 默认新建任务会话；单发适配器以独立 runId 记录执行。新增最小 `AgentRun`，包含 taskId、profileId、projectId、sessionId/runId、状态、开始结束时间、摘要与产物引用。

状态至少区分：待发送、执行中、待审批、成功、失败、已取消、状态未知。发送超时应先查询运行状态；只有桥接端支持 requestId 幂等后才能安全自动重发。AI 执行成功后进入“待验收”，由用户确认任务完成。

**参考：** Happy 的远程控制分工和 LibreChat 的生成任务/流恢复机制，支持把执行建模为可追踪运行，而非一次发消息。[Happy](https://github.com/slopus/happy)、[LibreChat](https://www.librechat.ai/docs/features/resumable_streams)

**验收：** 同时派发两项任务不会串会话；重复点击不重复执行；刷新后可继续追踪；明确显示失败或未知状态。

### P0-C：补齐恢复体验和数据结构校验

**代码事实：** `SyncConflicts.vue` 已保留双方，但展示原始 JSON，并仅支持选择本机或远端。备忘录与密码条目删除使用数组移除；周计划等已有局部撤销，但缺少统一、持久化的用户回收站。服务端变更历史不是面向用户的版本恢复界面。

另一个边界：`src/lib/syncMerge.ts:17` 校验了实体、版本、对象形状和附件描述，但不是所有业务字段的完整运行时校验；数据库水合对不同集合的归一化程度也不同。加密认证通过并不保证旧版或有缺陷客户端生成的业务数据符合当前模型。

**建议：**

1. 为实体建立版本化 schema、迁移和边界校验，覆盖导入、解锁和同步；未知版本保留原始密文并明确报错，不能默默丢弃字段。
2. 冲突界面改为字段差异，敏感值保持遮罩；先为备忘录、任务等增加“保留两个副本”。涉及关联或附件时重建引用，密码条目不自动混合字段。
3. 建立加密回收站与历史修订；恢复应产生符合现有协议的新操作，明确与墓碑的关系，不能靠移除墓碑让离线旧编辑复活。
4. 备份页显示内容范围、最近一次导出和最近一次恢复验证；“备份存在”与“恢复已验证”分别记录。

**参考：** Joplin 保存历史修订，恢复旧内容时另建恢复副本，保留当前版本。[历史版本设计](https://joplinapp.org/help/apps/note_history/)

**验收：** 误删、跨端删除冲突、恢复后再同步、旧 schema 导入和无效字段输入均有明确结果；恢复前后不破坏其他条目。

### P0-D：明确两种同步通道的安全边界

**代码事实：** 业务逐条同步已使用密文；AI 的 PocketBase 中继仍在 `src/lib/aiopencode.ts:469` 直接提交 `{ type, payload, status }`，没有对指令正文做应用层端到端加密。HTTP/TLS 和 Token 认证不等于中继无法读取内容。当前 AI 中继还复用了旧 `ensureSyncAuth()`，应与业务同步配置解耦，避免新旧同步体系的入口混淆。

**建议：** 面向异地远程使用前，完成可信 HTTPS 实网验收；AI 中继采用独立配对密钥和协议，绑定设备、会话、requestId、有效期及防重放信息。协议与现有密码库数据密钥隔离。审批请求应展示项目、操作、作用域，并支持查询和撤回持续授权。

v3 本机改密不会撤销已获得数据密钥的设备；后续设备管理应分别解决“撤销服务访问凭据”与“轮换数据密钥保护未来内容”。已经下载的旧数据无法通过远程撤销收回。

**参考：** Happy 的加密远程控制定位；Bitwarden 将账户加密密钥轮换作为独立生命周期处理。[Happy](https://github.com/slopus/happy)、[Bitwarden](https://bitwarden.com/help/account-encryption-key/)

此项是现有传输边界和后续设计建议，不是声称当前加密已被攻破。

## 5. 用户体验与产品结构

### P1-A：统一收集入口、全局搜索和跨模块引用

**代码事实：** `Task` 关联周计划/长期计划，但没有通用资料、备忘录、仓库引用。`MemosView.vue:116` 转任务会复制文本，没有保留 sourceMemoId。资料库搜索覆盖文件名、备注、标签，不搜索文件正文。各页面独立筛选，跨模块查找需要切页。

**建议分三步：**

- 先做全局搜索与统一新增入口，支持任务、便签、链接、文件，手机提供明显入口，桌面提供快捷键。
- 加入加密的 `EntityLink`，以实体类型和 ID 关联来源与目标。先支持“备忘录→任务”“任务↔资料”“任务↔仓库”，删除时显示失效引用，避免复制多份正文。
- 再做项目聚合页和收集箱，让用户可以先保存、后整理。项目收藏继续表示 GitHub 仓库，本地项目可关联一个或多个仓库。

首版全局搜索在解锁后建立内存索引，锁定清空；密码正文、TOTP 和连接 Token 默认不纳入通用搜索。若持久化索引，必须加密，不能把正文索引暴露给零知识服务器。

**参考：** Super Productivity 的任务/项目上下文，Memos 的快速记录，Karakeep 的跨类型收集与检索。[Super Productivity](https://github.com/super-productivity/super-productivity)、[Memos](https://usememos.com/docs)、[Karakeep](https://docs.karakeep.app/)

**收益：** “找资料、切页面、复制粘贴”的次数下降，现有功能能互相带动。

### P1-B：将精力规划从任务数量推进到时间容量

`src/stores/planning.ts:245` 当前按未完成任务数量计算负载，精力是排序依据之一；`Task` 没有预计时长。于是一个 5 分钟任务和一个 3 小时任务在负载上权重相同。

借鉴 Super Productivity 的时间盒，为任务增加可选 estimatedMinutes，为某天设置可用分钟；给温和/稳定/专注模式合理默认值，仍允许用户调整。排期同时考虑预计耗时、日期偏好、休息日和已锁定安排，容量不足时保留待安排项并解释原因。

先加预计时长和超载提示，后加实际耗时及周复盘；不要一开始增加大量番茄钟、绩效图和强制计时步骤。[参考项目](https://github.com/super-productivity/super-productivity)

验收要包括长短任务混合、全部休息日、容量不足、跨周重复、用户手动锁定任务；保留现有温和暂停与恢复体验。

### P1-C：资料库先全文检索，再考虑 AI 问答

借鉴 Paperless 的文本提取与原件保留，以及 Karakeep 的可搜索收藏。你已有 PDF/Office 预览基础，可先提取文本型 PDF、文本文件和文档正文，随后按需加入扫描件 OCR。[Paperless 文档](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/main/docs/usage.md)、[Karakeep](https://docs.karakeep.app/)

处理应在已授权的本机执行，提取结果加密保存；标记“待提取/处理中/失败/可搜索”。大文件提取需要可取消、可恢复的后台任务与资源上限。解密、索引、预览对象 URL 都应随锁定清理或中止。

后续 AI 检索只发送用户选定资料片段，展示来源文件/页码；密码库默认排除。不要为了全文搜索或 OCR 将明文传给现有零知识同步服务器。

### P1-D：让 Agent 资源库参与真实任务

当前 `AgentResource` 已有 useWhen、usage、compatibility、configSnippet 等丰富字段，适合继续发展成“经过验证的使用记录”。

新增最近验证时间、验证版本、适用项目和失败原因；派发任务时推荐关联资源，并记录这次运行使用了哪些配置。参考 LibreChat 的工具/Skills 选择与配置历史，但是否安装资源、是否执行配置必须受目标 Agent 的能力与用户授权约束。[Agents 文档](https://www.librechat.ai/docs/features/agents)

首版只做选择、配置预览和使用记录即可；“收藏了一条资源”不代表它已安装、可信或兼容。

## 6. 工程与性能

### P1：完善 AI 适配器能力声明与重连

当前 `aiopencode.ts` 777 行，`AiView.vue` 1142 行。`bridge/phub-bridge.mjs:506` 中 codex/dsh/zcode 实际仍是单发子进程；统一入口不代表五种 Agent 都具备完整会话、审批和 diff 能力。

建议拆为按 Agent 的 adapter、按通道的 transport 和公共运行状态层，统一声明 sessions、streaming、resume、approval、diff、files 等能力。UI 按能力呈现；静态 Agent 类型不应冒充运行时可用性。

当前 bridge 事件环仅保留 200 条且在内存中，进程重启后序号归零；pi UI 使用最大序号更新游标。应加入实例 epoch、事件范围/缺口检测和快照回补。重新连接本身不足以保证补齐事件。单发输出也需要独立运行归档，当前状态只暴露尾部 6000 字符。

LibreChat 的可恢复流提供“记录增量→重连补发→继续流式”的思路。它的默认模式也有内存状态，因此不能从功能宣传推断任意部署都保证崩溃后恢复；你的单机 bridge 可先选用小型持久日志，无需直接引入 Redis 集群。[可恢复流文档](https://www.librechat.ai/docs/features/resumable_streams)

### P1：附件按需下载、缓存和断点恢复

`attachmentSyncStore.ts` 每轮遍历资料，本机已有附件会完整解密检查，再散列分块并查缺块；`attachmentSync.ts` 下载分配整个密文缓冲区，完成后整体认证，失败不保留已下载块。

建议优先增加按描述版本记录的已验证状态、待传队列、分块下载暂存、手动/打开时/始终下载策略、明确的离线固定和缓存上限。缓存命中不能绕过内容变更或最终认证；临时块在完整验证前不可对外作为文件使用。

垃圾回收依赖历史版本、回收站、冲突、离线设备和备份保留策略；先设计保留窗口与安全裁剪边界，不要只看当前 DocMeta 引用就删块。[Joplin 附件策略](https://joplinapp.org/help/apps/attachments/)

50 MiB 验证已通过。下一步应测多附件总量和峰值内存，而不是重复证明单个 50 MiB 能传。当前每文件 GCM 模式无法仅靠网络分块获得真正分块解密；若未来更改加密格式，要另行设计认证清单、nonce 唯一性及版本迁移。

### P2：先测量整库保存开销，再决定粒度迁移

`src/stores/database.ts:126` 快照全部业务，`:156` 保存时加密整个 payload，`:262` 深度监听。网络协议已逐条化，但本地持久化仍是整库密文。数据增长后可能影响保存延迟和内存，这是结构性风险，尚无本次性能测量证明它已经成为瓶颈。

先以合成数据测 1 千/1 万/5 万条记录的编辑、保存、解锁和内存，再按瓶颈选择缓存快照、变更追踪或逐实体密文存储。若改为逐实体存储，业务记录、离线操作、回执和游标仍必须有可靠事务边界。

不要仅因三端应用就马上迁移原生 SQLite，也不建议现在全面改成 CRDT。现有个人单用户模型与显式冲突机制可继续迭代；多人实时编辑出现后再评估不同数据类型需要的合并算法。

建议补 `sync:typecheck`、隔离浏览器的关键同步/备份冒烟测试，以及规划、派发幂等、事件断档和单发失败路径测试。CI 为纯 Web 测试准备固定版本浏览器与明确依赖，不依赖某台机器的 npm 缓存。原生系统选择器、安装升级和 HTTPS 真机测试保留独立矩阵。

按下一次修改的边界拆 `TodayView.vue`（1417 行）和 `AiView.vue`，将规划与会话状态放入 composables；避免只移动代码而不建立行为测试。协议加入 schemaVersion 与兼容性测试，覆盖旧客户端读取新增字段。

## 7. 推荐实施顺序

工作量为相对判断，不是时间承诺。可在保留已有数据兼容性的前提下按以下四轮执行。

| 轮次 | 交付 | 工作量 | 完成标准 |
| --- | --- | --- | --- |
| 1：日常可靠性 | 前台周期拉取；附件检查不随空拉取全量运行；明确 AI 派发目标；schema 校验；校正当前能力说明 | 中 | 无操作也收更新；派发不串会话；无效记录不破坏解锁/同步 |
| 2：操作闭环 | AgentRun、事件缺口恢复、任务关联、统一搜索与快捷收集 | 中至大 | 刷新后能追踪任务；从任务找到原始资料和执行产物 |
| 3：长期使用 | 回收站/历史、字段冲突界面、附件按需下载和缓存、预计时长规划 | 大 | 误删能恢复；断网恢复不丢结果；任务安排能反映真实负载 |
| 4：异地与扩展 | 可信 HTTPS 实网验收、逐设备凭据、AI 中继 E2EE、推送、受控密钥轮换 | 大 | 真实远程链路通过；设备访问可管理；协议边界与恢复流程明确 |

若你已经准备通过公网日常远程控制电脑，第 4 轮的 HTTPS、AI 中继 E2EE 和认证隔离应提升到第 1 轮；不能因排期靠后就把当前明文应用层中继宣传为端到端加密。

建议第一个完整用户故事：**把一条备忘录转成任务，关联两份资料，选择开发机项目派发 AI；手机离线再回来能看到完整执行结果，确认后完成任务，保留来源和产物。** 这能同时检验各模块衔接，并形成与你已实现功能相符的产品特色。
