# 附件密文同步 · 第七阶段

连接新版逐条同步服务后，资料库文件可自动上传及下载，不再仅传文件列表。旧 PocketBase 整库同步不支持此功能。

## 工作流程

本机 AES-GCM 附件密文按最多 1 MiB 分块，每块计算 SHA-256。服务器按保险库归属保存不可变密文块；文件名、MIME、IV、密文总大小及分块清单位于加密的资料元信息内。服务端可见密文块大小、摘要和请求时序，不接收文件明文。

先同步记录，检查本机附件并上传缺失块，全部上传确认后更新加密元信息，再同步记录。其他设备收到描述后下载、校验各块摘要与长度，拼接并通过 AES-GCM 认证，最后事务保存完整密文到 IndexedDB。下载不完整或认证失败不会作为可用文件入库。

单文件仍为 50 MiB 上限（密文额外 16 字节）。服务端每个保险库密文总量暂限 1 GiB。上传在中断或重启后查询已有摘要，只补传缺失块；下载目前失败后重新下载整个文件，不持久化部分下载。附件失败显示错误，当前会话约 30 秒后再尝试。锁定、断开或维护期间停止后续处理；已到达服务器的不可变块可能保留。

历史本机文件会在同步时补充附件描述。仅有旧文件列表而没有本体的设备会明确提示先在源设备同步；不会把缺失文件当成空文件上传。更换远端附件描述时，不复用旧文件本体。备份恢复重加密后的密文将产生新摘要，后续同步发布新的描述。

## 删除与容量

删除记录继续通过墓碑传播。当前不会自动删除服务端块，也不会清理因远端删除产生的本机缓存：离线设备、冲突和旧备份可能仍引用它们。垃圾回收需要保留策略与恢复窗口，本阶段暂未实现。不要手工按当前记录列表删除服务端块。SQLite 数据目录整体备份应同时保留密文块与记录历史。

当前扫描所有本机资料，完整校验后查询分块；尚无后台任务、并行队列、下载缓存配额和用户选择仅 Wi-Fi 的开关。手机连接时可能使用移动流量，设置页已有说明。大文件的内存占用与真机性能尚需专项测试。

## 接口

握手返回 `attachments: true` 才启用附件 API。旧服务器会明确提示升级。

- `POST /v1/blobs/missing`：同一账号保险库内查询最多 51 个摘要。
- `POST /v1/blobs/put`：提交一块 Base64 密文，服务端验证规范编码、大小和 SHA-256，原子检查容量并幂等存储。
- `POST /v1/blobs/get`：按摘要取回密文块，需通过同一套账号和保险库权限检查。

## 验证

单元与 HTTP 集成测试覆盖分块传输、上传中断重试、服务重启持久化、跨账号拒绝、篡改摘要、GCM 密钥不一致、锁定停止、远端附件变更不复用旧文件。生产 Edge 双设备测试使用加入后新上传的跨分块文件，在另一设备下载并逐字节比对。

本次 17 个测试文件、130 项测试通过，前端生产构建和服务端类型检查通过。Edge 全流程记录：`.visual-qa/sync-1789868125271/report.json`，包括新附件跨设备逐字节比对及既有同步、冲突、断线和自动重连回归。前两次浏览器脚本分别因未等待附件上传和导航前未关闭设置弹窗而中止，修正脚本后完整重跑通过。

已重新构建并安装 Android Debug APK，运行新 Windows release exe，与 Edge 完成三端回归：手机、Windows 分别上传一个新 10 MiB 文件，另外两端解密后的字节数和 SHA-256 与原文件一致；两端进程重启后再次校验通过。记录位于 `.visual-qa/native-1789869163049/report.json`，页面运行时异常为零。
