# 离线同步基础 · 第一至四阶段

当前版本在没有服务器时也能准备同步记录；第五阶段已提供需主动连接的本机 HTTP 同步服务，详见 [SYNC-SERVER.md](./SYNC-SERVER.md)。下方保留前四阶段的实现记录。

## 已实现

第二阶段已将主信封、同步/GitHub/AI 加密凭据与锁定偏好迁入 IndexedDB 事务存储，详情见 [LOCAL-STORAGE.md](./LOCAL-STORAGE.md)。

第三阶段已加入可显式升级的 v3 密钥封装、设备独立密码和离线设备加入，详情见 [DEVICE-KEYS.md](./DEVICE-KEYS.md)。

第四阶段已实现持久化在途请求、增量合并、冲突界面与自动重试调度，详情见 [RECORD-SYNC.md](./RECORD-SYNC.md)。实际网络传输尚未接入。

- 在现有 v2 加密信封的 payload 中增加可选 `offlineJournal`，业务数据和队列一次落盘。
- 按 profile、entries、tasks、weeklyPlans、longPlans、planner、agentResources、agentResourceTaxonomy、memos、docMetas、repos 拆分逻辑记录。
- 使用 `[kind, id]` 的 JSON 编码作为记录身份，单例使用 `singleton`。
- 为每个待发送记录保存独立 operationId、deviceId、baseRevision、删除标记与内容。
- 尚未接入网络发送，连续离线修改合并为该记录的最新状态；删除保留 tombstone。
- 旧信封首次解锁时建立队列，保留业务时间戳，避免迁移被当成较新的业务更新。
- 设备 ID 单独保存在 `xk.device.id.v1`。其他设备导入备份时重新建立本机队列，不冒用原设备身份。
- 锁定清空内存队列与统计；改密、备份导出和恢复沿用信封加密流程。
- `lastRemindedTs`、附件本机 `blobId` 不进入新协议共享内容；旧整库同步仍包含这些本机字段。
- 设置页显示离线记录数量与最近保存时间；配置过服务器不会直接显示“已同步”。

## 协议边界

`syncProtocol.ts` 和 `offlineJournal.ts` 提供记录识别、队列准备与回执处理的纯逻辑。

`syncWire.ts` 将操作封装为 AES-GCM 密文，密文内同时包含操作标识、实体、设备和基础版本；解密时验证明文头与密文内容一致。生产接口不得直接发送 `SyncOperation.value`。

早期明文模拟服务器仅位于测试目录。第四阶段新增独立的密文模拟服务 `syncRehearsal.ts`，供设置页演练与测试使用，不提供网络监听。它验证原子版本检查、幂等重试、变更游标、删除冲突和同记录并发更新。

模拟服务的明文操作模型只用于测试。后续实际服务只保存密文及必要元数据，按已认证的数据空间隔离记录，不能信任客户端传入的 deviceId 作为权限证明。

第四阶段发送器已实现先持久化在途请求、再发送，回执原子提交后才发送依赖版本的下一操作。不能将演练服务作为生产服务器。

冲突回执保留双方，现已有冲突选择界面、分页解密合并和真实本机存储适配；实际网络传输尚未接入。

## 兼容性与限制

- 主信封与加密凭据使用 IndexedDB `xk-vault` 事务保存；附件继续使用 IndexedDB `xk-docs`。未迁移到原生 SQLite。
- 队列保存在密文内部，未新增业务内容的明文存储。指纹目前使用规范化 JSON，也位于密文内部；队列会增加信封体积，后续逐条数据库存储阶段应改为摘要并测量容量。
- 旧客户端不认识队列字段，重新保存时可能丢弃该字段。新版本可重新准备队列，但这不是跨版本协同保证。
- 既有 PocketBase 入口仍使用整库时间戳覆盖，其成功不清空新协议队列，不代表逐条同步成功。
- 附件本体尚无上传下载队列，仍需导出备份搬运。
- Web 多窗口提交现已使用事务版本检查：拒绝过期写入并允许导出冲突窗口备份，尚不自动合并。v3 已实现密码与数据密钥分离、离线加入；原生 SQLite、后台同步与真正的跨设备数据合并仍是后续工作。
- 本阶段不进行生产服务器部署，不创建云账号，不需要付费资源。
